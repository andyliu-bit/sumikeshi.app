# sumikeshi — PDF墨消しチェッカー / 墨消しツール

> 設計の前提は [PRODUCT.md](./PRODUCT.md)（誰に何を約束するか）と
> [DESIGN.md](./DESIGN.md)（配色・字送り・禁止事項）に置いている。
> UI を触る前に両方読むこと。

PDF の黒塗りが本当に効いているかを診断し、効いていないものを実際に削除する。

技術検証の経緯と踩んだ罠は [SPIKE.md](./SPIKE.md) を参照。

## 診断する3項目

| # | 項目 | 実装 |
|---|---|---|
| 1 | 黒塗りの下に残ったテキスト層 | ページを描画し、テキスト抽出できる矩形領域のコントラストを測る |
| 2 | ファイル内に残った削除前の原本 | (a) 孤児: trailer から到達可能なオブジェクトを辿り、非到達かつ文字描画命令を含む stream を検出 (b) 過去の版: 各 %%EOF で切った旧版を開き、今の版に無い行を検出 |
| 3 | メタデータ・埋め込みファイル | Info 辞書、XMP（カタログの /Metadata）、EmbeddedFiles |

項目2が本ツール固有の検出軸。**墨消し処理をしても保存時に garbage collection をしなければ、処理前の内容がファイル内に丸ごと残る。** 表示にもテキスト抽出にも現れないため通常の確認では気づけない（実測値は SPIKE.md）。

### 増分保存で残る過去の版

既存のオブジェクトを**同じ番号のまま**書き換えて増分保存すると、孤児は生まれない。旧版はファイル前半にそのまま残り、最初の `%%EOF` で切れば誰でも読める。孤児の走査だけを見ていた頃は、これを「問題なし」と判定していた（`test/versions.node.ts` で再現）。

**版の数では判定しない。** 実データ 6 件中 3 件（Word / Acrobat 出力）が最初から 2〜3 版あり、版の数で警告すると正常な公文書の半数に当たる。各版を実際に開き、**過去の版にあって今の版に無い行**が実在するときだけ報告する。実データでの誤報は 0 件。

墨消しの出力は gc 付きで全体を書き直すので常に 1 版になる。

### 孤児の中身の復元

「N 件残っています」だけでは利用者は動けない。**何が残っているか**まで見せる。

content stream 内の文字は glyph id なので、対応する Resources が無いと読めない。
ページの `Contents` を一時的に孤児と差し替え、そのページのフォント資源で解釈させる
（文書は保存しないので副作用は残らない）。

**どのページの資源で解釈するかの判定が肝。** 孤児がどのページの旧版かは分からないので
順に試すが、「最初に差分が出たページを採る」と事故る。資源が合わないページで解釈すると
glyph id の対応が狂って文字化けし、その文字化けが「消えた行」として報告される
（実データで `["3", "第", "４"]` のような断片が出た）。

そこで**現在の本文との重なり**で正しいページを選ぶ。孤児がそのページの旧版なら
現在の本文をほぼ全て含むので重なりは 1.0 近くになり、資源が合わなければ 0 近くになる。
閾値 0.6 未満なら**何も返さない**。壊れた文字列を「漏れている内容」として見せるのは、
残存を見逃すのとは別種の害になる。

表示するのは孤児の全文ではなく、**現在のページに無い行だけ**。全文を出すと通常の本文に
埋もれて、何が消し残っているのか読めなくなる。

なお**処理報告書には復元内容を載せない**（件数のみ）。報告書は回覧・保管されるため、
中身を書けば報告書自体が新たな漏洩源になる。

実データでは項目3が実際にヒットした。2007年の官公庁資料に職員番号らしき `Author`、
元の Word ファイル名（`Microsoft Word - 資料１－０４　会議等の公開について（案）.doc`）、
埋め込まれた Distiller 設定ファイルが残っていた。

### メタデータ文字列の復号

古い日本語 PDF は Info 辞書の文字列が **BOM 無しの Shift_JIS** で書かれていることがある。
mupdf は符号化を判定できず `<4D6963726F...>` という hex 文字列のまま返すため、
そのまま出すと診断結果に 16 進数が並ぶ。`decodePdfString()` で復号している。

**符号化を試す順序が重要。** UTF-8 を Shift_JIS より先に試さないと、
Shift_JIS はほぼ任意のバイト列を受理してしまい、UTF-8 の日本語が文字化けしたまま
「復号成功」になる（`議事録` → `隴ｰ莠矩鹸`）。順序は BOM → ASCII → UTF-8 → Shift_JIS → EUC-JP。

どれでも読めなければ**推測せず元の hex を返す**。壊れた文字列を見せるより、
「読めない値が入っている」と分かる方が診断として正しい。

## 墨消しの設計

**「消した」と主張せず、「消えた」ことを示す。** 処理後に必ず診断器へ通し、その結果を証拠として返す:

- 対象領域の再抽出 → 文字が取れないこと
- 孤児オブジェクト → 0 件であること
- メタデータ → 除去済みであること

3つとも通って初めてダウンロードボタンが出る。

## 処理報告書

監査・決裁・保管のための記録を HTML で出力する（`lib/certificate.ts`）。

記載するのは以下:

- ツール名とバージョン、処理日時
- 処理前後のファイル名・サイズ・**SHA-256**（同一性の担保）
- 削除箇所の一覧（ページ、位置、範囲、削除文字数）
- 検証結果 4 項目と合否
- 端末内処理である旨と、ツールの限界の明示

**削除した内容そのものは絶対に載せない。** 報告書は回覧・保管されるため、中身を書けば報告書自体が新たな漏洩源になる。記録するのは位置と文字数まで。この原則は `test/certificate.node.ts` で自動検証している。

PDF ではなく HTML で出す理由: mupdf-wasm には標準 14 書体しか入っておらず CJK フォントが無い（`gid(山)=0`）。ブラウザで日本語 PDF を直接生成するには数 MB のフォントを別途読ませる必要があり、割に合わない。HTML なら日本語描画は OS のフォントに任せられ、`@page` と `@media print` を持たせておけばブラウザの印刷機能から PDF として保存できる。

### 検証で気をつけた点

**全文検索で「消した文字列がまだ在るか」を見てはいけない。** 実文書ではタイトルが各ページのヘッダに繰り返し現れるため、消した箇所とは無関係な別ページの同一文字列を拾って誤判定する。

**単純な交差判定でも駄目。** ユーザーが引く矩形は行の途中や複数行にまたがるので、縁をかすめただけの隣接テキスト（消さないのが正しい）まで残存と判定してしまう。被覆率 50% 超を残存の基準にしている。

検証すべきは「囲んだ範囲の中身が消えたか」であって、縁に触れた要素の有無ではない。

## コンテンツページ

工具そのものはブックマークされない。保存され共有されるのはチェックリストや事例集の方なので、
流入口としてコンテンツを持たせている。

- `/cases` — 公表された漏えい事案。**出典が確認できたものだけ**を掲載する。一次情報を取れていないものは組織名の列挙にとどめ、まとめサイトへ誘導する（`content/cases.ts`）
- `/guide` — 公開前の自己点検 3 ステップと、正しい隠し方、よくある誤解

書き方は批判ではなく再発防止を目的とする。どの組織も公表と謝罪を済ませており、
狙いは「同じ構造の事故が繰り返されている」ことを示して読者の自己点検につなげること。

`NEXT_PUBLIC_SITE_URL` を設定すると sitemap / robots / metadataBase / OGP が全て追従する（`lib/site.ts`）。

黒塗りの下の行・gc 無し保存の孤児・架空の作成者名の 3 種類を含み、生成時に診断結果を自己検査する。

### OGP 画像

`node scripts/make-og.mjs` → `public/og.png`（1200x630）。文言を変えたら再生成する。

**内容は「黒塗りの下から個人情報が読めている」状態の図解。** 説明文ではなく状態を出す。
X やはてブのタイムラインでは縮小表示されるため、判断材料になるのは図と見出しだけになる。

next/og（Satori）を使わない理由: 日本語フォントを別途読ませる必要があり、
静的書き出しの構成では割に合わない。mupdf は既に依存にあり、システムの日本語フォントを
そのまま埋め込める（`new Font(name, ttc, subfont)` で `.ttc` から直接読める）。

黒地に載せる danger だけ DESIGN.md の値から明度を上げている。L=0.50 のままだと
黒地で対比 2.6:1 しか出ず、縮小表示で読めなくなるため。

## デプロイ

`output: "export"` で完全な静的書き出しをする。サーバーを持たない設計なので
API も middleware も無く、`out/` をそのまま静的ホスティングに置ける。

```bash
npm run build     # out/ に書き出し（約 17MB、うち 10MB は WASM）
npm run preview   # out/ を静的配信して http://localhost:3001 で確認
```

**本番に出す前に必ず `npm run preview` で確認する。** dev サーバーとは配信条件が違い、
特に WASM の MIME（`application/wasm`）と Worker の読み込みはここでしか再現しない。

### 静的書き出しで踏んだ点

- **`robots.ts` / `sitemap.ts` に `export const dynamic = "force-static"` が要る。**
  無いとビルドが `Failed to collect page data` で落ちる。
- **`public/` に置いたものは全て配信される。** 動作確認用のサンプル PDF を置いたままだと
  出力が 30MB になり、再配布しないと決めた公開資料まで含まれてしまう。
  確認用のファイルは `out/` に直接置く（`out/` は gitignore）。
- **プリフェッチは切っている**（`lib/link.tsx`）。理由はそのファイルのコメントを参照。

### ホスティング

静的ファイルを置ければどこでもよい。WASM が 10MB あるため、
1 ファイルの上限がある事業者だけ注意する（Cloudflare Pages は 25MB なので問題ない）。
転送時は事業者側で圧縮されるので実際のダウンロードは 3〜4MB 程度。

`NEXT_PUBLIC_SITE_URL` を設定してからビルドすること。sitemap と OGP の URL が
ビルド時に焼き込まれるため、後から変えるには再ビルドが必要。

## 構成上の判断

- **mupdf をバンドルしない。** `mupdf-wasm.js` に Node 判定下でのみ実行される `await import("module")` があり、バンドラが静的解決に失敗する。`public/mupdf/<version>/` に置いて `import(/* turbopackIgnore: true */ ...)` で実行時に読み込む。WASM ファイルの位置解決も同時に片付く。
- **mupdf のパスにバージョンを含める。** 10MB の wasm が既定の `max-age=0, must-revalidate` で配信されると、再訪のたびに再検証の往復が発生する。パスにバージョンが入っていれば内容が変わらないことを保証できるので、`public/_headers` で 1年 immutable を指定している。バージョンを上げれば URL ごと変わるため、新しい js と古い wasm が混ざる事故も防げる。
- **解析・描画・墨消しは全て Web Worker 内。** UI を止めないことに加え、ファイルがページ側から離れないことを保証する。ワーカーは文書を保持し、`open` / `render` / `analyze` / `redact` を id 付きで往復する。
- **`createAnalyzer(mu)` / `createRedactor(mu)` の工場形式。** Node（テスト）とブラウザ（ワーカー）で mupdf の入手経路が違うため、モジュールを引数で受け取る。
- **保存は必ず `compress,garbage=deduplicate`。** 裸の `saveToBuffer()` は禁止。外すと墨消しが無かったことになる。
- WASM は 10MB。ファイル選択後に初めてワーカーを作るので初回表示には影響しない。

## 誤検知対策で入れた判定

素朴に「テキスト抽出できるのにコントラストが無い」だけで判定すると、縦書き文書で誤検知が出る。mupdf は縦書きを 1 文字ずつ独立した line として返すため、「）」「。」のように字框内の墨の割合が極端に低い文字が引っかかる。

そこで **背景色との差** を条件に加えた。黒塗りは「背景と大きく異なる均一色」、空の字框は「背景と同色」で区別できる。これで実データの誤検知が 10 件 → 0 件になった。

また縦書きの検出結果は隣接判定で連結する。連結しないと「山」「田」「太」「郎」が 4 件並ぶだけで、何が漏れているのか読めない。

## メモリ管理（重要）

**mupdf のオブジェクトは明示的に `destroy()` しないと WASM ヒープに残り続ける。**

これを怠っていた時期の実測値: 379KB の PDF を 20 回診断しただけで external メモリが
1.9GB に達し、WASM がクラッシュした（1 回あたり約 97MB）。ピクスマップは A4 を 2 倍で
描画すると 1 ページ約 6MB あるため、解放しないと数十件で破綻する。

現在は `page` / `pixmap` / `StructuredText` / `PDFDocument` / `Buffer` / 注釈を
すべて解放しており、診断の繰り返しでは 50 回でも 48MB 前後で安定する。

ただし mupdf の JS 側ラッパは返り値ごとにオブジェクトを作り、その回収は
FinalizationRegistry 任せで時期が読めない。1 回あたり 1MB 前後は積み上がるため、
一括診断では 20 件ごとにワーカーを作り直してヒープを基準値に戻している
（`WORKER_RECYCLE_EVERY`）。

**新しく mupdf のオブジェクトを受け取るコードを書いたら、必ず解放を入れること。**

## 既知の限界

- **部分的な被覆は検出しない。** 黒枠が文字の一部からはみ出しているとコントラストが生じるため対象外になる。テキスト層は完全に抽出できるので漏洩ではあるが、現在の判定軸では拾えない
- **白文字を白背景に置く隠し方は検出しない。** 背景色との差が出ないため。別の判定軸（文字色と背景色の比較）が必要
- **スキャン画像内の文字は未判定。** OCR 併用の判断は保留
- **フォントサブセット残留。** 削除した文字だけが持つ字形が埋め込みフォントに残る
- **ライセンスの席数は技術的に強制していない。** 署名に席数を刻んではいるが、
  端末数を数える手段が無い（サーバーを持たない設計のため）。契約上の範囲として扱う
- **ファイルサイズ上限 150MB。** 超えると明示的に拒否する（`MAX_FILE_BYTES`）
- **非表示レイヤー（Optional Content）の文字は検出しない。** 既定で非表示のレイヤーに置かれた文字は画面に出ないが抽出はできる。全レイヤーを表示した状態との比較が必要
- **過去の版の比較は本文テキストだけ。** フォームの入力値や注釈（コメント）の文字は見ない。また最初の版と新しい側の 15 版だけを調べる
- **フォームを同じ値で上書き保存しただけの PDF を、孤児ありと判定することがある。** 外観ストリームの旧版が孤児になるため（内容は今と同じ）
- **利用者パスワード付きの PDF は診断しない。** 開けても中身を復号できず、そのまま進むと「検出なし」になってしまうため、明示的にエラーを返す

## 個人情報の自動検出

`lib/detect.ts`。文字単位の quad を使うため、行全体ではなく該当部分だけを囲める
（「氏名：山田太郎　電話：090-1234-5678」の電話番号だけを対象にできる）。

**書式で拾うもの**: 電話番号、郵便番号、メールアドレス、個人番号。
個人番号は検査用数字を検証する。これを省くと 12 桁の数字が全て拾われ、
金額や受付番号まで個人番号として扱われる。

**記入欄で拾うもの**: 「氏名：」「住所：」「連絡先：」のように項目名が付いた値。
項目名は日本語だけでは足りない。履歴書や名刺では「姓名：」「邮箱：」「Tel:」が
そのまま使われる。辞書に無いラベルがあると、直前のラベルの値が行末まで伸びて
次の項目まで巻き込む（実際に「電話：…　邮箱：…」が一つの範囲になる不具合が出た）。

**見出しとしての氏名**: 履歴書・名刺・署名では氏名にラベルが付かず、単独の行として
置かれる。姓の辞書（日本・中国の上位）と照合して拾う。誤検出を抑えるため、
行全体が 2〜5 文字かつ**漢字のみ**の場合に限る。漢字のみを条件にしないと
「方針の企業」のような一字姓で始まる語句を拾ってしまう（実測で発生した）。

**電話番号**: 区切りの有無、国際形式、日本と中国の携帯番号を扱う。
`0X0-XXXX-XXXX` だけを想定していると、履歴書によくある 11 桁連続表記
（`13800138000`）が丸ごと素通りする。

### 検出の順序

書式が明確なもの（メール・電話・郵便番号・個人番号）を**先に**確定させ、
そのあとに氏名、最後に記入欄を見る。逆順にするとラベルの値が広く取られ、
その中に含まれるメールアドレスなどが個別の候補にならない。

### 組織名は既定で検出しない

学校名・会社名それ自体は個人情報ではない。多くの文書では本文の一部であり、
消してはいけない。実測でも、議事録の「日本銀行」、白書の「東京大学」
「産業技術総合研究所」のように、残すべきものばかりが挙がった。

一方で履歴書・論文の査読・内部通報のように文書全体を匿名化したい用途では、
所属は準識別子になる（学校 + 専攻 + 入学年 + 成績の組み合わせで個人に辿り着く）。
そのため `includeOrganizations` を明示的に有効にしたときだけ検出する。
画面では既定でオフのチェックボックスとして出し、用途の違いを添えている。

接尾語の直後に漢字が続く場合は、より長い語の一部とみなして飛ばす。
これが無いと「全国大学生数学建模」から「全国大学」を切り出してしまう。

### 画像は検出できない

顔写真・印影・スキャンされた署名は画像であり、文字として拾えない。
埋め込み画像の個数を数えて画面に注意を出し、手動指定を促している。

### 検出は候補の提示までに留める

適用の可否は必ず人が選ぶ。消し漏らしは漏えい事故、消しすぎは情報公開請求への
不当な不開示であり、どちらもツールが独断で決めてよい範囲にない。
画面では候補を一覧にし、既定で全選択にしたうえで一件ずつ外せるようにしている。

### 行の境界を補っている理由

`walk()` は行の区切りを文字として返さない。そのままだと「住所：…」の値が次の行まで
繋がって読まれ、囲む範囲が二行にまたがる。字の上端 y の変化から改行を補うことで、
郵便番号が住所欄に飲み込まれる問題も同時に解消している。

## 課金の仕組み

アカウントもサーバーも持たない設計のため、**署名付きの文字列そのものをライセンスにしている**。

- 発行: `node scripts/issue-license.mjs "組織名" [--plan buyout|org] [--seats N]`
  秘密鍵は `.keys/`（gitignore）。発行記録は `.keys/issued.log` に追記される
- 検証: 内蔵の公開鍵で ECDSA P-256 の署名を確認する。**通信は一切発生しない**ため、
  外部と通信できない庁内ネットワークでも動作する
- 保存: localStorage。端末ごとに登録する

Ed25519 ではなく ECDSA P-256 を使っているのは、WebCrypto での対応が広いため。

### 転売への抑止を技術ではなく社会的なものに置いている

ライセンスに刻まれた組織名は画面と処理報告書に印字される。他所へ渡せば相手の報告書に
自組織名が載るため、B 向けでは実質的な抑止になる。技術的なコピー防止はブラウザ内で
完結する以上どうやっても破られるので、そこに労力を割いていない。

### 一括「墨消し」を提供しない理由

削除範囲の判断は人が行う必要がある。消し漏らしは漏えい事故だが、消しすぎも情報公開請求への
不当な不開示になる。一括で提供するのは診断（どのファイルに問題があるかの洗い出し）までとし、
墨消しは 1 件ずつ確認しながら行う。
